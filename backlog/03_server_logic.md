# Вертикаль: Серверная бизнес-логика (Ktor / Spring Boot)

## Задача 1. Слой ORM и Баз Данных (SQLite)
* Описание: Проектирование реляционных таблиц бэкенда для персистентного хранения сущностей документов.
* Подзадачи:
    - [ ] **Реализация Exposed (Ktor-Exposed / Spring-Exposed)**:
        - [ ] Описать объект `DocTable` с полями `id` (AutoIncrement Primary Key), `name` (String), `dateOfDoc` (String/Date).
        - [ ] Описать объект `DocRowTable` с полями `id`, `idDoc` (Foreign Key со стратегией `CascadeOnDelete`), `costType` (String/Enum), `costQuantity` (Double), `costPrice` (Double), `costSum` (Double), `meterReadingStart` (Double), `meterReadingEnd` (Double).
        - [ ] Написать SQL-запросы Exposed DSL для выполнения каскадного сохранения (insert/replace) и удаления.
    - [ ] **Реализация Hibernate (Spring-Hibernate)**:
        - [ ] Создать класс `@Entity DocEntity` со связью `@OneToMany(cascade = [CascadeType.ALL], orphanRemoval = true)`.
        - [ ] Создать класс `@Entity DocRowEntity` со связью `@ManyToOne`.
        - [ ] Объявить интерфейс `DocsJpaRepository`, расширяющий `JpaRepository`.

## Задача 2. Сетевой слой REST API и Логика Синхронизации
* Описание: Реализация HTTP-контроллеров, маршрутов и алгоритмов вычисления дельты данных для обработки запросов от клиентского приложения.
* Подзадачи:
    - [ ] Интегрировать сериализатор `kotlinx.serialization` для обработки JSON на стороне всех серверов.
    - [ ] **Для Ktor**: Настроить DSL-методы `get`, `post`, `put`, `delete` в функции `configureRouting`.
    - [ ] **Для Spring Boot**: Создать классы `@RestController` с аннотациями `@GetMapping`, `@PostMapping`, `@PutMapping`, `@DeleteMapping`.
    - [ ] Реализовать сквозные контракты онлайн-API (CRUD):
        - [ ] `GET /api/docs` -> Возврат списка всех сущностей из БД бэкенда.
        - [ ] `POST /api/docs/list-by-ids` -> Прием списка идентификаторов записей -> Возврат массива соответствующих сущностей целиком за один запрос.
        - [ ] `POST /api/docs/save` -> Прием новой КМР-модели -> Запись в БД.
        - [ ] `PUT /api/docs/update` -> Прием измененной КМР-модели -> Полная перезапись существующей сущности в БД.
        - [ ] `DELETE /api/docs/{id}` -> Удаление сущности и связанных строк из БД по `id`.
    - [ ] **Реализация единого эндпоинта синхронизации (`POST /api/sync`)**:
        - [ ] Настроить прием входящего тела запроса, содержащего текущий массив данных клиента (`List<Doc>`) и выбранный режим `SyncMode` (`FULL` или `ID_ONLY`).
        - [ ] Реализовать алгоритм сверки на бэкенде: сервер анализирует присланные данные, обновляет устаревшие записи у себя и вычисляет дельту — то, чего не хватает на клиенте по сравнению с актуальной серверной БД.
        - [ ] Реализовать ветвление формата ответа в зависимости от полученного `SyncMode`:
            - При режиме `FULL`: вернуть клиенту массив недостающих объектов `Doc` целиком.
            - При режиме `ID_ONLY`: вернуть клиенту исключительно список идентификаторов записей, которых ему не хватает.
