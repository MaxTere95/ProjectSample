# Стандарты кодирования (Code Style)

При генерации любого Kotlin/Kotlin DSL кода ты обязан строго соблюдать правила форматирования, именования и документирования, заложенные в этом шаблоне.

## 3.1 Правила комментирования кода (КРИТИЧЕСКИЙ ПРИОРТЕТ)

Ты обязан строго соблюдать правила комментирования логики. За любые нарушения пул-реквест будет отклонен:

1. **Абсолютный запрет на inline-комментарии справа:**
   - Категорически запрещено писать любые комментарии справа от кода на той же строке (через `//` или `/* */`).
   - *Пример КАК НЕЛЬЗЯ ПИСАТЬ:*
     ```kotlin
     val currentID = 1L // Начальный ID для строк счетчиков
     ```

2. **Правило переноса комментариев наверх:**
   - Все поясняющие комментарии должны располагаться СТРОГО на отдельной строке (или нескольких строках) НЕПОСРЕДСТВЕННО НАД целевым кодом, к которому они относятся.
   - *Пример КАК НАДО ПИСАТЬ:*
     ```kotlin
     // Начальный ID для строк счетчиков коммунальных услуг
     val currentID = 1L
     ```

3. **Смысловая нагрузка:**
   - Комментарии должны описывать бизнес-причину ("почему" логика написана именно так), а не пересказывать синтаксис языка Котлин ("что" делает функция). Если код очевиден из названий переменных — комментарий не пишется.

## 3.2 Стандарты форматирования кода и чистота структуры

При генерации Котлин-файлов или Gradle-скриптов ты обязан строго соблюдать следующие правила разметки:

1. **Размер отступов (Indentation):**
   - Всегда используй ровно 4 пробела для отступов блоков кода в Kotlin-файлах и файлах конфигурации `build.gradle.kts`.
   - Использование знаков табуляции (`\t`) запрещено.

2. **Очистка пустых строк:**
   - Категорически запрещено оставлять пробелы или знаки табуляции на пустых строках (trailing whitespaces). Пустые строки между функциями должны быть абсолютно чистыми.
   - Между логическими blocks внутри одной функции допускается не более одной пустой строки.

3. **Расстановка фигурных скобок:**
   - Открывающая фигурная скобка `{` всегда ставится на той же строке, где объявляется класс, функция или управляющая конструкция (`if`, `when`, `for`), через один пробел.
   - Закрывающая скобка `}` всегда переносится на отдельную строку и выравнивается по началу конструкции.

## 3.3 Стандарты именования для Серверного слоя (Backend)

При генерации серверного кода (Ktor / Spring Boot) строго придерживайся следующих соглашений:

1. **Базы данных и ORM (Exposed / Hibernate):**
   - Объекты таблиц Exposed DSL должны оканчиваться на `Table` в PascalCase (например, `DocTable`, `DocRowTable`).
   - Классы сущностей Hibernate / JPA должны оканчиваться на `Entity` (например, `DocEntity`, `DocRowEntity`).
   - Названия колонок в Exposed и полей в Hibernate должны быть в camelCase (совпадать с доменными моделями).

2. **Сервисы и Репозитории бэкенда:**
   - Интерфейсы серверных репозиториев должны иметь суффикс `ServerRepository` (например, `DocsServerRepository`).
   - Сервисы бизнес-логики (ядра бэкенда) должны иметь суффикс `Service` (например, `SyncService`).

3. **Сетевые эндпоинты (Routing / REST):**
   - Маршруты Ktor описываются внутри экстеншенов `Route` или `Application` в нижнем регистре через дефис (например, `/api/docs/list-by-ids`).
   - Классы контроллеров Spring Boot помечаются аннотацией `@RestController` и должны оканчиваться на `Controller` (например, `DocController`).
